# 테스트 도입 및 층 분리 계획

작성일: 2026-07-30
대상: old-hanja (한문독해 앱, https://old-hanja.pages.dev)
스택: Astro + Cloudflare Pages + D1, TypeScript

## 배경

지금까지 분석 정확도 문제(不 독음 규칙, 어순재구성 few-shot 예시의 之 누락,
절 단위 대괄호, 부정사 붙여쓰기, max_tokens 부족 등)를 사람이 통제 실험을
반복 측정하는 방식으로 하나씩 찾아 고쳤다. 결과는 좋았지만, 프롬프트나 로직을
고칠 때마다 같은 수동 검증을 다시 해야 한다.

오픈소스 프로젝트 rhwp(Rust+WASM 기반 아래한글 HWP 뷰어/에디터)가 같은 종류의
문제를 다루는 방식을 참고한다. rhwp는 "한컴이 그린 것과 픽셀 단위로 같아야
한다"는, 정답 확인이 어려운 문제를 다음 방법으로 해결했다.

1. 층을 나눠 한 번에 한 층만 상대한다 (파서 / 문서모델 / 조판 / 렌더러)
2. 테스트 5,500개 + 시각 회귀 테스트로 한 번 잡은 버그를 못 박는다
3. 코드를 고치지 않고 원인 층을 좁히는 디버그 도구를 갖춘다
4. 안 되는 것은 경고하고 차단한다 (보존 불가 요소는 저장 거부)

이 문서는 그 네 가지를 한문 앱에 옮기는 계획이다.

## 목표 구조

현재는 분석 API 한 파일 안에 아래 여섯 가지가 섞여 있다고 추정된다.
이를 분리해서, 매번 결과가 달라지는 구간을 한 칸으로 격리하는 것이 목표다.

```
[결정론적 — 테스트 가능]
  1. 정규화        이체자·공백·구두점 정리
  2. 힌트 감지     허사·문형 사전 조회 → 프롬프트 힌트
  3. 프롬프트 조립 문자열만 반환, 네트워크 접근 없음
        ↓
[비결정론적 — 이 한 칸만]
  4. AI 호출       Anthropic API
        ↓
[결정론적 — 테스트 가능]
  5. 응답 파싱     JSON → 타입
  6. 검증          이탈도 판정 (기존 validate.ts)
  7. 화면 표시     경고 함께 노출
```

용어:
- 결정론적(deterministic): 같은 입력이면 항상 같은 결과. 테스트로 고정 가능.
- 순수 함수(pure function): 입력만 받아 결과만 반환. 네트워크·DB·시계를 건드리지 않음.
- 불변조건(invariant): 결과가 무엇이든 반드시 참이어야 하는 조건.
- 회귀(regression): 고쳤던 버그가 다시 살아나는 것.

## 진행 규칙

- 단계별로 세션과 브랜치를 나눈다. 한 세션에서 여러 단계를 동시에 하지 않는다.
- 각 단계는 실행 전에 수행계획서를 작성하고 승인을 받는다.
- 파일 경로는 이 문서의 추정이 섞여 있다. 실제 구조를 먼저 확인하고,
  다르면 계획서에 실제 경로를 적어 보고한 뒤 진행한다.
- 완료 후 PR로 main에 병합한다. 커밋이 origin/main의 조상인지 확인한 뒤
  로컬 브랜치·원격 브랜치·worktree를 삭제한다.

## 2단계: 회귀 테스트 — 이미 잡은 버그 못 박기

브랜치: `add-vitest-tests` (1단계와 같은 브랜치)

과거에 실제로 발생했던 오류 사례를 테스트로 고정한다. AI 출력은 매번 문장이
달라지므로 "정답과 글자까지 일치"는 검사할 수 없다. 대신 반드시 지켜져야 하는
불변조건만 검사한다. rhwp의 시각 회귀 테스트에 대응하는 장치다.

### 작업

`tests/invariants.test.ts` 신규 생성.

```ts
import { describe, it, expect } from 'vitest';

const 원문 = '知之爲知之不知爲不知';
const 재구성결과 = '[知之爲知之] [不知爲不知]';

describe('어순재구성 불변조건', () => {
  it('한자 개수가 원문과 같아야 한다', () => {
    const 추출 = 재구성결과.replace(/[^\u4e00-\u9fff]/g, '');
    expect(추출.length).toBe(원문.length);
  });

  it('之가 누락되지 않아야 한다', () => {
    const 원문之 = (원문.match(/之/g) || []).length;
    const 결과之 = (재구성결과.match(/之/g) || []).length;
    expect(결과之).toBe(원문之);
  });

  it('부정사(不·未·非·勿)가 뒤 글자와 붙어 있어야 한다', () => {
    expect(재구성결과).not.toMatch(/[不未非勿][\s\]]/);
  });
});
```

기존 `src/lib/validate.ts` 의 판정 함수(`judgeRepair` 등)도 직접 import 해서
테스트한다. 이탈도가 줄어든 경우 통과, 늘어난 경우 실패를 각각 확인한다.

추가로 넣을 사례 (과거 실제 발생한 것들):
- 不 독음 규칙 — 앱에서 채택한 규칙을 그대로 테스트로 표현
- 절 단위 대괄호 — 절 개수와 대괄호 쌍 개수 일치
- "한자(풀이)" 표기 순서 — 정규식으로 형식 검사

### 완료 조건

- `npm test` 로 위 테스트가 모두 통과한다.
- 일부러 값을 틀리게 바꿨을 때 해당 테스트가 실패하는 것을 확인한다.
  (통과만 확인하면 테스트가 실제로 아무것도 검사하지 않는 경우를 놓친다.)

## 3단계: 프롬프트 조립을 순수 함수로 분리

브랜치: `extract-prompt-builder`

> **이 절은 실제 구조를 확인한 뒤 고쳐 적었다.** 원래 본문은 앱 내부를 모르는 상태로
> 쓴 것이어서 세 가지가 사실과 달랐다. (1) mode 이름이 `basic`/`precise` 가 아니라
> `light`/`deep` 이다. (2) 정밀 모드는 프롬프트를 늘리는 방식이 아니라 모델을 바꾸는
> 방식이므로 `precise.length > basic.length` 예시는 성립하지 않는다. (3) 옮길 "프롬프트
> 문자열 조립 코드"가 사실상 없었다 — 프롬프트는 이미 상수였고, 실제로 흩어져 있던 것은
> 요청 파라미터였다. 그래서 함수를 `buildPrompt` 하나가 아니라 두 개로 나눴다.

### 찾을 곳

`src/pages/api/analyze.ts`. Anthropic **SDK** 로 호출한다(`fetch` 가 아니다).

```ts
const stream = client.messages.stream(params as never);
```

그 위쪽에서 `params` 를 만드는 다섯 줄과 deep 모드의 `thinking` 분기가 옮길 대상이다.
`SYSTEM_PROMPT` 와 `ANALYSIS_SCHEMA` 는 이미 `src/lib/analysis.ts` 의 모듈 상수이므로
"백틱으로 감싼 긴 문자열을 함수 안으로 넣는" 작업은 없다. 상수를 파일째 옮기고,
**요청 파라미터 조립**을 함수로 감싸는 것이 이 단계의 실질이다.

허사·문형 힌트는 프롬프트에 들어가지 않는다. 허사·문형 매칭은 별도 엔드포인트
`src/pages/api/pos.ts` 에서 화면 표시용으로만 쓴다. 그래서 `PromptInput` 에 `hints` 를
두지 않는다 — 쓰이지 않는 매개변수가 되고, 넣는 것은 동작 변경이라 이 단계 범위가 아니다.

### 작업

`src/lib/prompt.ts` 신규 생성. `SYSTEM_PROMPT` · `ANALYSIS_SCHEMA` 를 내용 변경 없이
옮기고, 조립 함수 둘을 둔다.

```ts
import { maxTokensFor, type Mode } from './analysis';   // Mode = 'light' | 'deep'
import { extractHanja } from './hanja';

export interface PromptInput {
  text: string;   // 정규화된(normalize 를 거친) 한문 구절
  mode: Mode;
}

/** 프롬프트 문자열만. 네트워크·DB·시계를 건드리지 않는다. */
export function buildPrompt(input: PromptInput): { system: string; user: string };

/** SDK 에 그대로 넘길 요청 파라미터. 역시 순수 함수. */
export function buildAnalysisRequest(input: PromptInput, model: string): Record<string, unknown>;
```

함수를 둘로 나누는 이유: **실제로 사고가 났던 곳이 프롬프트 내용이 아니라 요청
파라미터였다.** `max_tokens` 를 4000 으로 고정해 두어 긴 구절의 JSON 이 잘렸고, 교정
호출의 `max_tokens` 700 을 sonnet 의 사고 토큰이 다 먹어 교정이 3/3 무효였다. 그쪽을
테스트로 감싸지 않으면 이 단계에서 얻는 것이 거의 없다.

한자 수는 인자로 받지 않고 `text` 에서 직접 구한다. 인자로 받으면 실제 입력과 어긋난
값을 넘길 수 있고, 그러면 응답이 잘린다.

`analyze.ts` 는 호출만 남긴다.

```ts
import { buildAnalysisRequest } from '../../lib/prompt';

const params = buildAnalysisRequest({ text, mode }, model);
const stream = client.messages.stream(params as never);
```

재수출(`analysis.ts` 에서 `export { SYSTEM_PROMPT } from './prompt'`)은 두지 않는다.
import 경로가 둘로 갈리는 것이 이 프로젝트가 반복해서 다친 형태다. 사용처를 직접 고친다.

`prompt.ts → analysis.ts → hanja.ts` 단방향을 유지한다. `analysis.ts` 가 `prompt.ts` 를
import 하면 순환이 된다.

### 프롬프트 동일성을 어떻게 증명하는가

"눈으로 diff 를 봤다"로는 부족하다. 두 겹으로 본다.

**겹 1 — 파일 스냅숏.** 리팩터링에 손대기 **전** 커밋에서 요청 전체를 파일 스냅숏으로
뜬다(`tests/__snapshots__/request-{모드}-{길이}.txt`, 구절 2개 × 모드 2개 = 4건).
담는 내용은 `keys` 줄 / `model` / `max_tokens` / `thinking` 유무 / `system` 의 length·
sha256 / `system` 전문 / `messages` 전문 / `output_config` 다. 리팩터링 커밋에서 조립부만
`buildAnalysisRequest()` 호출로 바꾸고,

```bash
git diff --exit-code <기준선커밋> <리팩터링커밋> -- tests/__snapshots__/
```

가 무변경이면 요청이 바이트 단위로 같다. 구절을 둘 쓰는 이유는 한자 수에 비례하는
`max_tokens` 를 고정하기 위해서다.

**겹 2 — 리팩터링 전 소스와 직접 대조.** 겹 1 에는 구멍이 있다. 기준선을 뜰 때 테스트에
베낀 조립 코드가 애초에 `analyze.ts` 와 달랐다면, 잘못된 기준선을 그대로 재현하며
통과한다. 그래서 `git show <전>:src/lib/analysis.ts` 를 꺼내 새 `prompt.ts` 와 직접
대조한다 — `SYSTEM_PROMPT` 문자열 완전 일치(length + sha256 + `===`), `ANALYSIS_SCHEMA`
구조 완전 일치, 요청 파라미터 깊은 동등 + 키 순서 동일. 일회성이므로 커밋하지 않는다.

**ANALYSIS_VERSION 은 올리지 않는다.** 프롬프트가 바이트 단위로 같으므로 기존 캐시가
여전히 유효하다. 올리면 캐시가 통째로 무효가 되어 재분석 비용만 발생한다. 동일성 증명이
곧 "버전을 올릴 필요가 없다"는 근거다.

### 테스트 배치

프롬프트 **내용**에 관한 검사는 모두 `buildPrompt()` 를 거치게 한다. 상수를 직접 보면
나중에 `buildPrompt` 안에서 조건에 따라 일부를 빼거나 덧붙여도 눈치채지 못한다.
프롬프트와 무관한 검사(`maxTokensFor`, `predictCostUsd`, `ANALYSIS_SCHEMA`,
`ANALYSIS_VERSION`, 정규식 대조군)는 그대로 상수를 직접 본다.

전환하면 "상수를 우회하고 다른 문자열을 내보내는" 경우를 아무도 보지 않게 되므로,
**브리지 테스트 한 건**을 둔다. 이것이 유일한 상수 동일성 검사다.

```ts
it('system 은 SYSTEM_PROMPT 를 그대로 내보낸다', () => {
  expect(buildPrompt({ text: '學而時習之', mode: 'light' }).system).toBe(SYSTEM_PROMPT);
});
```

`tests/prompt.test.ts` 는 조립 자체를 본다 — `max_tokens` 가 실제 한자 수에서 계산되는지,
`deep` 에만 `thinking:disabled` 가 붙고 `light` 에는 키 자체가 없는지, 실려 나가는 키가
정해진 것뿐인지(`temperature` 등이 조용히 끼어드는 것도 잡는다), 그리고 순수성.

모드에 관한 검사는 이렇게 적는다. 원본 계획서의 `precise.length > basic.length` 를
대체하는 것이다.

```ts
it('모드가 system 프롬프트를 바꾸지 않는다 — 정밀 모드는 모델을 바꾼다', () => {
  const light = buildPrompt({ text: '學而時習之', mode: 'light' });
  const deep = buildPrompt({ text: '學而時習之', mode: 'deep' });
  expect(deep.system).toBe(light.system);
  expect(resolveModel('deep', {})).not.toBe(resolveModel('light', {}));
});
```

### 완료 조건

- 프롬프트와 요청 파라미터가 리팩터링 전과 완전히 동일하다 (분리 시점에는 내용을
  바꾸지 않는다. 동작 변경과 구조 변경을 한 커밋에 섞지 않는다).
- 위 두 겹의 증명이 모두 통과한다. 스냅숏 diff 무변경을 커밋 사이에서 확인한다.
- `prompt.ts` 와 `analysis.ts` 사이에 순환 참조가 없다.
- 배포 후 **이미 캐시된 구절 하나를 재조회**해서(0원, `cached=true`) 앱이 정상 동작함을
  확인한다. 바이트 동일성이 요청은 보장하지만, import 경로 수정으로 인한 번들링·모듈
  해석 문제는 덮지 못한다. 유료 분석 1건은 이 목적에 필요하지 않다.
- `npm test` 통과, `npm run check` 0 errors.

## 4단계: 캐시 키와 버전 통합

브랜치: `unify-cache-key`

> **이 절은 실제 구조를 확인한 뒤 고쳐 적었다.** 원래 본문은 앱 내부를 모르는
> 상태로 쓴 것이어서 네 가지가 사실과 달랐다. (1) 캐시 키를 만드는 곳은 이미
> 한 곳뿐이었다. (2) 키는 조인 문자열이 아니라 SHA-256 다이제스트이고, 함수는
> 비동기여야 한다. (3) `ANALYSIS_VERSION`은 숫자가 아니라 문자열이고, mode는
> `basic`/`precise`가 아니라 `light`/`deep`이다. (4) 구분자 U+0000 문제는 이미
> 공백으로 고쳐져 있었다. 예시 코드를 그대로 따랐다면 원문이 키 컬럼에 실려
> 스키마 주석(`text_hash` = 정규화된 원문의 SHA-256)이 깨졌을 것이다.
>
> **이 단계는 앞의 세 단계와 달리 실제 동작이 바뀐다.** 1~3단계는 "동작을 바꾸지
> 않는다"가 안전장치 그 자체였다(2단계는 버그를 알면서도 기록만 했고, 3단계는
> 바이트 동일성으로 증명했다). 4단계는 정규화 결과와 캐시 키가 의도적으로 달라진다.
> 그래서 커밋을 **동작 불변 / 동작 변경** 두 덩어리로 쪼개고, 달라진 것이 정확히
> 무엇인지를 테스트 목록으로 고정한다.

캐시 키 버그를 두 차례 겪었다. (1) mode(정밀분석 토글)가 키에 빠져 있었음,
(2) ANALYSIS_VERSION이 키에 없어 로직 개선 후에도 낡은 결과가 서빙됨.
원인은 같다 — 결과를 결정하는 요소가 여러 곳에 흩어져 있어 사람이 기억해야 했다.

### 현재 구조 (착수 전 확인)

캐시 키를 만드는 곳은 `src/pages/api/analyze.ts` 한 곳뿐이다.

```ts
const textHash = await sha256(`${ANALYSIS_VERSION} ${mode} ${text}`);
```

"모든 위치를 교체한다"는 전제는 이미 충족돼 있다. 그래도 분리할 값어치는 있다 —
지금은 라우트 핸들러 안에 인라인이라 테스트가 하나도 붙어 있지 않고, 두 번 겪은
사고를 막는 것이 주석 한 줄뿐이다.

프로덕션 D1 규모: `analyses` 17행, `search_logs` 24행.

### 작업

**커밋 A — 조립을 함수로 분리 (동작 불변)**

`src/lib/cache-key.ts` 신규 생성.

```ts
export async function cacheKey(text: string, mode: Mode): Promise<string> {
  return sha256(`${ANALYSIS_VERSION} ${mode} ${normalize(text)}`);
}
```

- 해시를 유지한다. 조인 문자열을 그대로 키로 쓰면 원문이 `analyses.text_hash`에
  실려 컬럼의 의미와 스키마 주석이 함께 깨진다.
- 키 형식(구분자 공백)은 바꾸지 않는다. 구분자를 바꾸면 그것만으로 전 캐시가
  무효가 된다. 무효화의 원인을 버전 인상과 정규화 변경 둘로만 한정한다.
- `normalize()`를 함수 안에서 부른다. 호출자가 정규화를 잊으면 눈에 똑같은 구절이
  다른 키를 받아 두 번 과금된다 — 정확히 이 단계가 막으려는 사고다.
- `analysis.ts`는 `cache-key.ts`를 import하지 않는다(순환 방지). 3단계와 같은 규칙.

동작 불변의 증명은 **프로덕션 D1에 실재하는 행의 `text_hash`를 골든값으로 박는
것**이다. 오라클이 내 계산이 아니라 프로덕션 데이터다. 다만 그 구절은 이미
정규화된 값이라 `normalize` 호출 여부를 가리지 못하므로, 정규화가 실제로 값을
바꾸는 입력(`'  學而   時習之  '`)으로 `cacheKey(raw) === cacheKey(normalize(raw))`를
따로 검사하고, `normalize`의 멱등성도 함께 못박는다.

**커밋 B — normalize() 수정 (동작 변경)**  → 아래 "추가 항목" 참조

**커밋 C — ANALYSIS_VERSION 이동 + 인상 (동작 변경)**

`analysis.ts` → `cache-key.ts`로 옮긴다. 이 상수를 소비하는 곳이 캐시 키뿐이므로
키를 만드는 함수 옆에 두는 것이 "통합"의 실질이다.
값: `'v3-repair-budget'` → `'v4-zerowidth-normalize'`.
골든 해시 테스트가 여기서 깨지는 것이 정상이다. 새 값으로 갱신하고, 옛 값은
"낡은 캐시가 다시 잡히지 않는다"는 검사로 남긴다.

### 기존 캐시 행은 어떻게 되는가

**17행 전부 미스로 버려진다. 마이그레이션은 하지 않는다.**

불가능하기 때문이다 — 키 재료에 mode가 들어가는데 `analyses` 테이블에 mode 컬럼이
없다. `model`로 역추정(haiku→light, sonnet→deep)할 수는 있으나
`ANTHROPIC_MODEL_DEEP`으로 모델을 갈아끼울 수 있어 보장이 아니다. 해시는 단방향이라
행에서 재료를 복원할 수도 없다.

버리는 것이 맞기도 하다. 배포 검증에서 프로덕션 캐시가 돌려준 어순 재구성이
`알다(知)는(之)`처럼 "풀이(한자)" 역순이었다 — 그 규칙이 프롬프트에 들어가기 전에
저장된 행이다.

비용: 재분석은 사용자가 그 구절을 다시 조회할 때만 발생한다(선결제 없음).
최악의 경우 light 기준 $0.011 × 17 ≈ 270원. 낡은 행은 지우지 않는다.
`search_logs.text_hash`도 낡은 해시를 가리키지만 `recentSearches()`가
`original_text`로 묶으므로 화면에 영향이 없다.

### 테스트 (`tests/cache-key.test.ts`)

각 검사가 막는 사고를 한 줄로 적는다.

| 검사 | 막는 사고 |
|---|---|
| 골든 해시 = 프로덕션 행의 값 | 의도치 않은 키 변경이 조용히 배포되는 것 |
| 키는 버전·mode·정규화된 원문으로 조립된다 | 필드가 재료에서 빠지는 것 |
| mode가 다르면 키가 다르다 | 실제 사고 (1) |
| 옛 버전(v3)의 키와 다르다 | 실제 사고 (2) |
| 정규화 전/후 원문이 같은 키 | 호출자가 정규화를 잊는 것 |
| 폭 없는 문자가 낀/안 낀 원문이 같은 키 | 같은 구절 이중 과금 |
| 64자 16진 문자열 | DB 컬럼 계약 위반 |
| 원문이 키에 실리지 않는다 | 해시를 조인 문자열로 되돌리는 회귀 |

※ 처음에는 버전 검사를 `expect(키).not.toBe(다른 버전으로 만든 해시)`로 적었는데,
돌연변이 검사에서 **키에서 버전을 빼도 이 검사가 깨지지 않았다.** 부등호로는
"필드가 재료에 들어 있다"를 증명할 수 없다. 조립식을 직접 못박는 형태로 바꿨다.

### 추가 항목: normalize()의 U+FEFF 처리 (2단계에서 발견)

캐시 키는 정규화된 원문으로 만든다. 따라서 normalize()의 결과가 갈라지면 캐시 키도
갈라진다. 2단계에서 normalize()에 테스트를 붙이는 과정에 다음을 발견했다.

`src/lib/analysis.ts`의 normalize()는 세 단계로 되어 있다.

```
① .replace(/\s+/g, ' ')      공백 정리
② .replace(/[…]/g, '')       폭 없는 문자 제거 — 문자 클래스가 소스에
                              보이지 않는 문자 그대로 적혀 있어 읽을 수 없다.
                              실제 내용은 U+200B-U+200D 와 U+FEFF 다.
③ .trim()
```

②의 문자 클래스에 U+FEFF가 적혀 있지만 **②는 U+FEFF를 볼 일이 없다.**
①이 먼저 돌고, 자바스크립트 `\s`의 정의에 U+FEFF가 포함되기 때문이다.
(`\s`의 폭 없는 문자 범위는 U+2000-U+200A에서 끝나므로 U+200B-U+200D는 포함되지
않는다. 그래서 ②는 그 셋에 대해서만 실제로 작동한다.)
즉 ②에 적힌 U+FEFF는 닿지 않는 코드다.

실측한 현재 동작:

| 입력 | 결과 | 평가 |
|---|---|---|
| 글자 사이의 U+200B/200C/200D | 제거됨 | 의도대로 |
| **글자 사이의 U+FEFF** | **공백 한 칸으로 바뀜** | 의도와 다름 |
| 앞뒤의 U+FEFF | 공백이 된 뒤 ③에서 사라짐 | 무해 |
| U+2060 (WORD JOINER) | 그대로 남음 | 범위 밖 |

따라서 웹에서 복사한 원문에 U+FEFF나 U+2060이 끼어 있으면, 사람 눈에는 똑같은
구절인데 정규화 결과가 달라진다. 캐시 키가 갈라져 같은 구절이 두 번 과금되고,
폭이 없어 화면에 보이지 않으므로 사람이 알아채기 어렵다.

이 프로젝트가 보이지 않는 문자로 헤맨 세 번째 사례다. 앞의 둘은 한자 범위를 리터럴로
적다가 U+F900 대신 U+8C48을 쓴 것(한글이 한자로 판정됐다), 캐시 키 조립 문자열에 널
문자 U+0000이 구분자로 들어가 정규식 교체가 세 번 실패한 것이다.

2단계에서는 동작 변경과 구조 변경을 섞지 않기 위해 **고치지 않고 현 동작만**
`tests/normalize.test.ts`에 기록해 두었다. 캐시 키를 손대는 이 단계에서 함께 고친다.

#### 이 단계에서 할 일 (커밋 B)

- 폭 없는 문자 제거(②)를 공백 정리(①)보다 **먼저** 돌린다. 순서만 바꾸면 U+FEFF가
  공백이 되는 문제가 사라진다.
- 제거 범위에 **U+2060-U+2064를 넣는다.** 전부 폭이 없고 한문 구절에서 의미를 갖지
  않는다. 남겨두면 U+FEFF와 똑같은 방식으로 캐시 키를 가른다.
  - 일부러 넣지 않는 것: **변이 선택자(U+FE00-FE0F)와 IVS(U+E0100-)** — CJK 이체자를
    구분하는 데 실제로 쓰이므로 지우면 다른 글자가 같은 키로 합쳐진다. 이 앱은
    `source_guess.note`로 이체자 메모를 받는다.
    **U+00AD SOFT HYPHEN** — 폭이 없지 않다(줄바꿈 위치에서 하이픈으로 보인다).
- 문자 클래스를 **`\u` 이스케이프로 다시 적는다.** 지금은 무엇이 걸러지는지 소스를
  읽어서 알 수 없다. `src/lib/hanja.ts`가 같은 이유로 이스케이프 표기를 강제하고 있다.
- 고치면 `tests/normalize.test.ts`의 "현 동작 기록" 테스트가 실패한다. 그것이 정상이다.
  기대값을 새 동작으로 갱신하고, 주석에 적힌 사고 이력은 남긴다. 갱신 대상은
  **기대값이 바뀌는 2건**(U+FEFF, U+2060), **문구만 바뀌는 1건**(앞뒤 U+FEFF — 결과는
  같지만 이유가 "공백이 된 뒤 trim"에서 "애초에 제거"로 달라진다), 나머지 9건은 그대로.
- 정규화 결과가 달라지므로 기존 캐시 행은 자연히 미스가 된다. ANALYSIS_VERSION도
  함께 올려 두면 낡은 행이 다시 조회될 여지가 없다(커밋 C).

**소스 표기 규칙을 기계가 지키게 한다.** "보이지 않는 문자를 리터럴로 적지 않는다"는
규칙이 주석으로만 있었는데, 이 작업 중에 실제로 문자 클래스를 고쳐 적다가
U+200B·U+200D·U+2060·U+2064·U+FEFF를 리터럴로 써 넣는 일이 벌어졌다. 눈에 보이지
않으니 코드 리뷰로 잡히지 않는다. 소스를 코드포인트로 훑는 검사를 넣는다.
(`node:fs`가 아니라 Vite의 `?raw` 임포트를 쓴다 — tsconfig의 `types`에 `@types/node`가
없어 `astro check`가 막힌다.)

### 완료 조건

- 캐시 키를 만드는 코드가 프로젝트 전체에서 이 함수 한 곳뿐이다.
- ANALYSIS_VERSION을 올리면 다음 조회에서 캐시 미스가 나는 것을 확인한다.
  - 0원 증명: 새 키를 계산해 원격 D1에 그 `text_hash`가 **없음**을 조회로 보인다.
  - 왕복 증명: 프리뷰에 배포해 옛 캐시 구절을 1건 실제 분석시킨다(약 15원).
    미스 → 분석 → 새 키로 저장 → 재조회 `cached:true` 까지 확인한다. 낡은 결과가
    영구 서빙된 사고가 **쓰기 경로**에서 났으므로 미스 확인만으로는 부족하다.
- 폭 없는 문자가 낀 원문과 끼지 않은 원문이 **같은 캐시 키**를 만든다.
- normalize()의 문자 클래스에 보이지 않는 문자가 리터럴로 남아 있지 않다.
- `analysis.ts`와 `cache-key.ts` 사이에 순환 참조가 없다(탐지기로 확인하고,
  인위적 순환을 만들어 탐지기가 살아 있음도 함께 확인한다).
- 돌연변이 검사에서 각 돌연변이가 **의도한 테스트**를 깨뜨린다. 골든 해시만 깨졌다면
  그 테스트는 무효라는 뜻이므로 별도로 표시하고 고친다.
- `npm test` 통과.

## 5단계: 디버그 화면

브랜치: `add-debug-view`

rhwp는 코드를 한 줄도 고치지 않고 원인 층을 좁히는 절차를 갖췄다
(`--debug-overlay` → `dump-pages` → `dump`). 그 대응물을 만든다.

### 작업

`?debug=1` 쿼리가 붙었을 때 API 응답에 `debug` 필드를 포함시키고,
화면 하단에 표시한다.

담을 내용:
- 원문과 정규화 결과 (나란히)
- 감지된 허사·문형 힌트 목록
- 실제 전송된 프롬프트 전문
- AI 원본 응답 (파싱 전)
- 검증 이탈도 점수, 교정 시도 여부
- 캐시 히트 여부, ANALYSIS_VERSION, 사용 토큰 수

### 보안

프롬프트 전문이 노출되므로, 환경변수 `DEBUG_KEY` 와 일치하는 값을 함께
넘겼을 때만 동작하게 한다. 값이 없거나 틀리면 debug 필드를 아예 생성하지 않는다.

### 완료 조건

- `?debug=1` 만으로는 아무것도 보이지 않는다 (키 없이는 차단).
- 올바른 키로 접근했을 때 위 항목이 전부 보인다.
- 이 화면만 보고 "어느 층에서 틀렸는지" 판단이 가능하다.
